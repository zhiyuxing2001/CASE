> CASE — Clinical Archives for Student Encounters
> 中医跟诊病案数据库与跟师学习管理系统

| 项 | 内容 |
|---|---|
| 文档版本 | v2.0（两阶段规划） |
| 状态 | 待评审 |
| 部署形态 | **纯单机 Mac 本地工具**（不做多人/权限） |

## 一、项目定位

### 1.1 一句话定义

把中医学生跟诊时产生的**纸质处方、手写病历、随手笔记**，转化为**可检索、可溯源、可复用**的结构化病案数据库，并在其上提供跟师学习与 AI 辅助写作能力。

### 1.2 要解决的三个真实痛点

| 痛点 | 现状 | CASE 的解法 |
|---|---|---|
| **记录散失** | 跟诊笔记写在纸上/拍在手机里，学期末找不到、翻不动 | 拍照即入库，结构化 + 全文检索 |
| **结构缺失** | 笔记是自由文本，无法回答"老师治胃脘痛常用哪几味药" | 四诊/辨证/治法/方药结构化建模 |
| **学习不闭环** | 跟完诊就结束，没有心得沉淀、没有导师反馈 | 跟诊记录 → 心得 → 导师点评 → 病种覆盖统计 |

### 1.3 设计原则（贯穿全部决策）

1. **本地优先**：数据库、原始图片、导出物全部留在本机；上云仅限必要时，且默认脱敏。
2. **离线可降级**：断网时病案录入、检索、macOS OCR、导出必须照常工作，只有 AI 功能降级。
3. **人工终审**：AI 只做"建议填充"，任何写入数据库的病案字段都必须经过人工确认。
4. **可溯源**：每个结构化字段都能追回"哪张图的哪一行"，方便日后回看原始处方。
5. **不为标准化牺牲录入速度**：字典表做辅助建议，绝不因"不在字典里"而阻止录入。
6. **数据先行**：先把数据库设计做扎实并通过验证，再在其上开发软件。

### 2.2 阶段一：数据库设计

**为什么单独成为一个阶段**：中医病案的数据结构复杂度远高于普通业务系统 —— 四诊、辨证、方药、跟师关系各有其内在结构，中药还存在同名异物/同物异名问题。**数据结构一旦定型，后期修改成本极高**（涉及迁移、数据清洗、界面与统计联动）。因此先把数据基础做扎实。

**主要工作**：

| 步骤 | 内容 |
|---|---|
| 1. 需求分析与实体识别 | 对照《中医病历书写基本规范》等规范确认必填项与字段 |
| 2. 概念模型 | ER 设计、实体关系评审 |
| 3. 标准编码适用性 | 确认 ICD-11 TM / GB-T 等标准的适用范围（**仅预留，不强制**） |
| 4. 逻辑模型 | 34 张表的表结构、字段类型、约束、外键策略、索引 |
| 5. 检索设计 | FTS5 中文全文检索 + 按查询长度路由 |
| 6. 数据治理 | `audit_log` 字段级留痕、软删除、隐私字段设计 |
| 7. 字典与种子数据 | 中药/别名、证型、方剂、舌象脉象、炮制用法 |
| 8. 验证 | DDL 可执行性回归、约束/级联/触发器/检索路由测试 |

**交付物**：SQLAlchemy 模型 · Alembic 迁移 · 字典表种子数据 · 数据字典文档 · 数据库层测试

> 详细设计见 [`phase-1-database-design.md`](./phase-1-database-design.md)。

### 2.3 阶段二：软件开发

**主要工作**（六个批次）：

| 批次 | 内容 |
|---|---|
| B1 脚手架 | 项目结构、一键启动、配置管理 |
| B2 病案界面 | 录入 / 详情 / 检索 |
| B3 OCR 流水线 | 评测基线 → 双通道识别 → 校对界面 |
| B4 学习模块 | 跟诊记录 / 心得 / 导师点评 / 进度看板 |
| B5 AI 辅助 | RAG 问答 / 写作辅助 / 脱敏留痕 |
| B6 导出与交付 | 导出 / 备份 / 联调试用 / 文档 |

**交付物**：可运行的完整应用（后端 API + Web 界面 + OCR + AI 辅助）

> 详细设计见 [`phase-2-software-development.md`](./phase-2-software-development.md)。

### 2.4 阶段依赖与门禁

- **硬依赖**：阶段二的数据层直接使用阶段一的产出，**不存在并行开发**。
- **阶段门禁**：阶段一必须满足全部下列条件才可进入阶段二 ——
  - [ ] 全部 DDL 可执行，Alembic 迁移可正向/回滚
  - [ ] 约束、级联、软删除行为经测试验证
  - [ ] FTS5 触发器同步正确，**2 字词检索路由经回归测试**
  - [ ] 字典表种子数据入库可用
  - [ ] 数据字典文档完成
- **唯一例外**：**PREP-03（采集 OCR 评测集）必须与阶段一并行启动**。真实病案照片只能由使用者提供，若等阶段二再开始采集，会直接阻塞 OCR 开发。

## 三、范围界定

### 3.1 MVP 必须做（In Scope）

| 模块 | 能力 | 所属阶段 |
|---|---|---|
| **A. 病案结构化录入与检索** | 病案 CRUD；四诊、辨证、治法、方药结构化字段；中文全文检索 + 组合筛选；修改留痕 | 阶段一（数据）+ 阶段二（界面） |
| **B. 图片上传 + OCR 自动转病案** | 图片上传/拍摄；macOS Vision 粗识别；DeepSeek 精修结构化；置信度高亮校对界面 | 阶段二 |
| **C. 跟师学习模块** | 跟诊记录（日期/老师/科室/病种）；学习心得（富文本）；导师点评；学习进度统计 | 阶段二 |
| **D. DeepSeek 辅助** | 基于个人病案库的资料问答（RAG）；经典文献查阅；心得草稿生成与润色 | 阶段二 |
| **E. 数据导出与备份** | 按条件导出 Excel / Word 医案集；整库备份与恢复 | 阶段二 |

### 3.2 明确后置（v1.1+）

- **统计分析可视化**（证型分布、药物频次、方剂规律、师生用药对比）—— 数据结构预留，界面后置
- 中药知识图谱 / 方剂配伍网络图
- 病案批量导入（历史纸质档案扫描归档）
- jieba 预分词的高级检索引擎
- 打包为独立 `.app`（免终端启动）

### 3.3 明确不做（Out of Scope）

- ❌ 多用户、账号体系、权限控制（已确认纯单机）
- ❌ 云同步、移动端 App、Web 公网部署
- ❌ 舌象/脉象图像分析、AI 辅助辨证结论（**合规红线：不做诊疗决策输出**）
- ❌ 电子处方流转、对接医院 HIS/LIS 系统
- ❌ 多模态语音问诊记录

> **合规底线**：CASE 是**学习记录工具**，不是医疗器械、不做辅助诊断。所有 AI 输出必须标注"仅供学习参考，不作为诊疗依据"。

## 四、技术选型

### 4.1 选型总表

| 层 | 选型 | 理由 / 备注 |
|---|---|---|
| 运行时 | Python 3.13（项目内 `.venv`） | 本机 miniconda 为 3.13.13；**不要污染 base 环境** |
| Web 框架 | FastAPI + Uvicorn | 类型安全、自动 OpenAPI 文档、异步适配 LLM 调用 |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic | 迁移可回溯，schema 演进安全（阶段一核心） |
| 数据库 | SQLite（本机文件 `data/case.db`） | 已核实 3.51.2，FTS5 可用 |
| 全文检索 | **FTS5 `trigram` 分词器 + LIKE 回退** | 含已验证的坑，见 [`phase-1-database-design.md`](./phase-1-database-design.md) §4.2 |
| 前端 | React + TypeScript + Vite + **Ant Design** | AntD 表单/表格/Upload 组件成熟，中文场景原生，适合表单密集型系统 |
| 前端数据层 | TanStack Query + Axios | 缓存/失效/重试开箱即用 |
| LLM SDK | `openai`（OpenAI 兼容协议） | 指向 `https://api.deepseek.com`，官方推荐方式 |
| OCR 引擎 | **ocrmac**（封装 macOS Vision） | 已验证可用，见 [`technical-validation.md`](./technical-validation.md) |
| 导出 | openpyxl（Excel）、python-docx（Word） | 均为纯 Python |
| 配置 | pydantic-settings + `.env` | API Key 不进 Git |
| 测试 | pytest + pytest-asyncio；Playwright（可选 E2E） | |
| 启动 | `./run.sh` 一条命令起前后端，浏览器访问 `127.0.0.1:<port>` | **仅绑定 localhost**，不对局域网暴露 |

### 4.2 DeepSeek 模型能力与路由（已核实官方文档）

| 模型 | 视觉 | 上下文 | 输出长度 | 适用场景 |
|---|---|---|---|---|
| **`deepseek-flash`**（DeepSeek-V4.1-Flash） | ✅ **支持** | 1M | 384K | **OCR 结构化主力**、资料问答、心得润色 |
| `deepseek-v4-pro`（V4-Pro-0813） | ❌ 不支持 | 1M | 384K | 复杂辨证推理、长文档综述、系统性总结 |

两个模型均支持 **JSON Output**、**Tool Calls**、**上下文硬盘缓存**。

**成本估算（空闲时段）**：缓存命中输入 0.02 元/M tokens，未命中 1 元/M，输出 4 元/M。
一张处方图的视觉输入上限约 1024 tokens。**单张处方 OCR 成本约 0.002–0.01 元**，一个学期几百份病案的成本在几元量级，**成本不构成约束**。

> 实用结论：缓存命中价差 50 倍，意味着**固定 system prompt 前缀必须字节级稳定**（把字典表、字段说明放在最前面），可把重复输入成本压到 1/50。

### 4.3 已验证的环境事实

| 事实 | 结论 |
|---|---|
| macOS 26.5.2 / Apple Silicon | ✅ |
| `/usr/bin/python3` 与 conda python **均无** pyobjc/Vision | 需在项目 venv 内安装 `ocrmac` |
| `ocrmac` + pyobjc 在本机安装并运行成功 | ✅ 中文识别置信度 1.0，**逐行返回 confidence + bbox** |
| SQLite 3.51.2，FTS5 + trigram 可用 | ✅ 但 2 字查询静默失效（见阶段一文档 §4.2） |
| 环境变量中无 `DEEPSEEK_API_KEY` | ⚠️ 需用户到 platform.deepseek.com 申请并写入 `.env` |

## 七、验收标准（Definition of Done）

MVP 完成的判定：

- [ ] **阶段一**：全部 DDL 可执行；Alembic 迁移可正向/回滚；FTS5 触发器同步正确；2 字词检索路由经回归测试；字典种子数据可用；数据字典文档完成
- [ ] 能用手机拍一张手写处方 → 上传 → 自动填充结构化病案 → 校对 → 入库，**全程 < 2 分钟**
- [ ] 能按"证型 / 药物 / 时间 / 带教老师 / 关键词"组合检索，且 2 字词检索结果正确
- [ ] 一次完整跟师流程可记录：跟诊记录 → 学习心得 → 导师点评 → 进度可见
- [ ] 能就自己的病案库向 AI 提问，并得到**带出处引用**的回答
- [ ] 能导出一份可直接打印的 Word 医案集与 Excel 数据表
- [ ] 备份文件可在另一台 Mac 完整还原
