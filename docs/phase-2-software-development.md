## 一、阶段目标

在阶段一确定的数据库之上，交付一个**可日常使用**的单机应用，完成这条闭环：

> 拍一张手写处方 → 本地 OCR 粗识别 → DeepSeek 精修结构化 → 人工校对 → 入库 → 检索 / 学习 / 写成心得 / 导出

### 1.1 交付物清单

| # | 交付物 | 判定标准 |
|---|---|---|
| 1 | FastAPI 后端服务 | `./run.sh` 一键启动，仅绑定 `127.0.0.1` |
| 2 | Web 前端界面 | 病案录入/详情/检索/OCR 校对/学习/AI 六大页面可用 |
| 3 | OCR 双通道流水线 | 真实处方图 → 结构化字段，字段准确率达标 |
| 4 | AI 辅助模块 | 病案库问答（带出处引用）、心得写作辅助 |
| 5 | 导出与备份 | Word 医案集可打印；整库可异机还原 |
| 6 | 测试与文档 | pytest 覆盖核心服务；README 可自助上手 |

### 1.2 阶段出口标准

- [ ] 拍一张手写处方 → 上传 → 自动填充 → 校对 → 入库，**全程 < 2 分钟**

- [ ] 所有 AI 输出页面有"仅供学习参考"声明

### 2.3 架构要点

> **`adapters/` 是唯一允许接触外部系统（macOS API、DeepSeek 网络、文件系统）的地方。**

这条边界带来三个直接收益：

1. **离线降级只需改一处** —— 网络不可用时，`DeepSeekClient` 返回降级信号，上层无需感知；
2. **单元测试无需真实外部依赖** —— mock 适配层即可测全部业务逻辑；
3. **将来更换 OCR 引擎或模型供应商，不影响业务代码**。

## 三、模块设计

### 3.1 后端 API 层

按领域划分路由，统一响应格式与错误处理：

| 路由前缀 | 职责 |
|---|---|
| `/api/cases` | 病案 CRUD、检索、修改历史 |
| `/api/encounters` | 跟诊事件 |
| `/api/learning` | 学习笔记、导师点评、进度看板 |
| `/api/ocr` | 图片上传、识别作业、校对提交 |
| `/api/ai` | 问答、写作辅助、对话留痕 |
| `/api/export` | Excel / Word 导出、备份恢复 |
| `/api/health` | 健康检查 |

### 3.2 病案录入与检索界面

- **录入表单**：基本信息 + 四诊分区 + 诊断/治法（字典联想）+ 处方编辑器（动态增删药味）
- **处方编辑器**是录入体验的关键：一次 15 味药的录入必须流畅，支持剂量单位、炮制、先煎后下的快速选择
- **检索**：按查询长度路由（详见阶段一检索设计），支持证型/药物/日期/带教老师组合筛选
- **详情页**：完整病历视图 + 内嵌原图查看器 + 修改历史

### 3.3 OCR 流水线（核心技术方案）

这是本项目技术含量最高、也最容易失败的部分，因此单独详述。

#### 3.3.1 双通道设计

```
① 上传图片
   └─ 格式归一（HEIC→JPEG，Pillow/sips）、EXIF 旋转矫正
   └─ 质量闸门：Laplacian 方差判模糊，过糊直接提示重拍  ← 省掉后面全部无效成本
        │
        ├──────────────► ② 通道 A：本地 macOS Vision（ocrmac）
        │                  · 输出 [{text, confidence, bbox}]
        │                  · 快（<1s）、免费、离线、逐行置信度
        │
        ├──────────────► ③ 版面重建
        │                  · 按 bbox 的 y 坐标聚类成行、x 排序
        │                  · 识别版块：主诉 / 现病史 / 四诊 / 诊断 / 治法 / 处方 / 用法
        │
        └──────────────► ④ 通道 B：deepseek-flash 视觉精修
                           · 输入 = 【原图】 + 【通道 A 的文本与坐标】 + 【目标 JSON Schema】
                           · 任务 = 纠错 + 药味切分 + 术语归一 + 字段结构化
                           · 用 JSON Output 强约束输出结构
                                │
                                ⑤ 置信度融合与字典校验
                                   · Vision 行置信度 × 模型自评置信度
                                   · 药名/证型/方剂与字典表比对 → 建议归一
                                   · 低于阈值的字段标记为「待校对」
                                        │
                                        ⑥ 前端校对界面
                                           · 左图右表，低置信字段黄色高亮
                                           · 键盘流录入（Tab/Enter 快速跳转）
                                                │
                                                ⑦ 人工确认入库
                                                   · 写 cases / prescriptions / items
                                                   · 同时保存 raw_ocr_text + attachment_id 溯源
```

#### 3.3.2 为什么"双通道"明显优于单通道

| 方案 | 问题 |
|---|---|
| 只用 DeepSeek 视觉 | 纯生成，**会幻觉出并不存在的药名**，且无法给出字符级定位 |
| 只用 macOS Vision | 只出文本流，**不做结构化**，且会破坏排版（实测把 `白芍15g枳壳10g` 粘连） |
| **双通道融合** | Vision 提供**确定性的字符与坐标**，模型在其约束下做**纠错与结构化**，幻觉空间被大幅压缩 |

**实测证据**（立项验证）：macOS Vision 对印刷体中文病历识别置信度普遍 1.0，但在处方行输出为
`处方：柴胡10g 白芍15g枳壳10g 甘草6g` —— **药味与剂量的切分粘连**，无法直接入库。这正是通道 B 必须存在的理由：把 Vision 的文本与坐标作为上下文交给 `deepseek-flash`，让它输出 `[{herb:"柴胡",dose:10,unit:"g"}, ...]`。

#### 3.3.3 提示词与 JSON Schema 约定

- 提示词模板放 `backend/prompts/`，**按版本号入库**，每次结构性识别都记录用了哪个版本的提示词，便于回归对比。
- 输出 schema 与数据库字段一一对应，字段附带 `confidence` 与 `evidence`（引用 Vision 的哪一行）。
- **固定前缀（字典表 + 字段说明）必须字节级稳定**，以命中 DeepSeek 上下文缓存（输入价差 50 倍）。

#### 3.3.4 校对界面（决定实际可用性）

OCR 的终点不是"识别出来"，而是"学生愿意用它代替手工录入"。因此校对界面必须做到：

- 左右分栏：左原图（可缩放/旋转），右结构化表单
- 低置信字段黄色高亮，可一键采纳字典建议
- 键盘流跳转（Tab/Enter），校对一份处方 < 1 分钟

### 3.4 跟师学习模块

- **跟诊记录**：日期、带教老师、科室、病种标签，一次跟诊关联多份病案
- **学习心得**：Markdown 富文本，自动保存草稿，与病案双向引用
- **导师点评**：独立条目，与心得并列展示，**与 AI 生成内容视觉区分**（数据库层已用 `is_ai_generated` 标记）
- **学习进度看板**：累计跟诊次数、病案数、病种覆盖度、心得篇数，并提示覆盖缺口

### 3.5 AI 辅助模块

| 能力 | 说明 |
|---|---|
| 病案库问答（RAG） | 基于个人病案检索，**回答必须带出处引用**（来自哪份病案） |
| 经典文献查阅 | 条文检索、方剂出处、中药功效 |
| 心得写作辅助 | 基于选定病案生成初稿、润色、学术化改写（保留学生原意） |
| 术语归一建议 | 录入时提示"生地 → 生地黄" |
| 模型路由 | `deepseek-flash` 用于视觉与日常；`deepseek-v4-pro` 用于复杂推理（**不支持图片**） |
| 脱敏中间件 | 发送前替换患者姓名/电话 |
| 留痕 | 全部对话入库，`learning_notes.is_ai_assisted` 标记 AI 参与 |

> **合规底线**：AI 输出必须标注"仅供学习参考，不作为诊疗依据"。CASE 不是医疗器械，不做辅助诊断。

### 3.6 导出与备份

- **Excel**（openpyxl）：病案表 + 药味明细表，多 sheet，可直接筛选分析
- **Word**（python-docx）：按筛选条件成册的医案集，排版规范、可打印、含原图
- **备份**：`VACUUM INTO` 导出数据库 + `attachments/` 打包，提供恢复校验

## 四、离线降级与容错

| 情况 | 降级行为 |
|---|---|
| 无网络 / API 报错 | 自动切换为「仅通道 A」：Vision 文本直接填入自由文本域，结构化字段留空待人工 |
| API Key 未配置 | 应用正常启动，AI 相关入口显示「未配置 Key」引导，其余功能全可用 |
| 图片过糊 | 拒绝 OCR，提示重拍并给出拍摄建议 |
| SQLite 写锁 | 单用户场景风险低，仍做短事务 + 重试 |

> 核心功能（录入、检索、macOS OCR、导出）**零依赖网络**，这是本地优先原则的落地检验。

## 五、质量与测试策略

| 层 | 策略 |
|---|---|
| 数据层 | 约束、级联、触发器、FTS 同步的集成测试（阶段一已建立基础） |
| 服务层 | pytest 单测，适配层 mock，覆盖检索路由、字典归一、置信度融合 |
| OCR | **独立评测集 + 字段级准确率指标**（见 §5.1），每次改提示词都回归 |
| 前端 | 关键路径手工验收 + 可选 Playwright E2E |
| 交付前 | 数据完整性自检脚本（孤儿记录、缺失图片、索引一致性） |

### 5.1 OCR 质量评测（阶段二最前置的工作）

在写 OCR 代码前，**先攒一个 30–50 张真实病案照片的评测集**，量化：

- 字符级：CER（字符错误率）
- 字段级：四诊/证型/药味/剂量的**完全匹配率**
- 目标：印刷体字段准确率 ≥ 95%；手写体首轮 ≥ 80%，**经校对界面后入库数据 100% 正确**

> ⚠️ **最大风险提示**：立项阶段的 OCR 验证用的是**印刷体合成图**，结论**不能推广到手写体**。手写中医处方笔画潦草、简写连笔普遍，是全项目最大不确定项。
>
> 因此本阶段**第一件事就是跑基线**（仅 Vision / 仅 DeepSeek / 双通道三组对比）。**若手写体准确率远低于 80%，应在此处停下重新评估产品形态**（例如退化为"AI 只做自由文本转录、结构化纯人工"），而不是埋头做完才发现方向错了。
