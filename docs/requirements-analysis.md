## 一、解析方法（可复现）

两份材料均为**纯扫描件、无文本层**（`pypdf` 提取文本为 0 字符，全部内容为嵌入位图）。因此采用：

```
PDF ─► 抽取每页最大嵌入图片（跳过页眉 logo）
    ─► Pillow 存为 PNG
    ─► macOS Vision OCR（ocrmac，language=zh-Hans）
    ─► 输出 [{text, confidence, bbox}] 逐行结果
    ─► 人工比对原图核验
```

工具：[`tools/pdf_ocr_extract.py`](../tools/pdf_ocr_extract.py)

```bash
python tools/pdf_ocr_extract.py INPUT.pdf OUTPUT_DIR
```

**这一步本身就是阶段二 OCR 流水线的预演**，因此解析过程中暴露的问题具有直接的设计价值（见 §七）。

## 二、样本形态解析

两份材料代表了**两种截然不同的数据来源**，这正是本项目数据模型必须同时容纳的两端。

### 2.1 样本 A：跟师学习临床医案（手写填表）

- **载体**：印刷模板表单 + 手写填写，3 页
- **性质**：**教学属性**为主 —— 是师承教育的记录工具，不是医院文书

**表单印刷栏位（即模板结构）**：

| 页 | 栏位 |
|---|---|
| 1 | 患者姓名 · 性别 · 出生年月 · 就诊日期 · 主诉 · 现病史 · 既往史 · 过敏史 · 望闻切诊 · 辅助检查 · 西医诊断 · 中医诊断 · 辨证分析 · 治法 · 处方（"方拟\_\_\_\_加减治之"） |
| 2 | 复诊日期（第 1 次） · 复诊日期（第 2 次） |
| 3 | **心得体会** · 签名/日期 · **指导老师点评** · 指导老师签名/日期 |

**由此确认**：跟师学习记录 = 病案主体 **+ 学习元数据**（心得体会、导师点评、双签名）。后两者在普通门诊病历中完全不存在。

**观察到的重要数据质量问题**：

> 填写内容**并不严格遵循字段语义**。例如「过敏史」栏被填入了甲状腺结节检查结果，而真正的体格检查内容同时出现在「望闻切诊」和「辅助检查」两栏。

**设计含义**：不能假设"字段名 = 内容语义"。解析时必须容忍错栏，数据结构必须允许同类信息出现在多个位置，**归一化只能发生在人工校对环节，不能自动强判**。

### 2.2 样本 B：HIS 门诊病历 + 医嘱明细

- **载体**：医院信息系统（HIS）打印/截图，11 页
- **性质**：**临床属性**为主 —— 标准医疗文书，无教学元数据

**页构成**：

| 页 | 内容 |
|---|---|
| 1–5 | **门诊病历**，每次就诊一页。栏位：医院 · 表单名 · 姓名 · 就诊卡号 · 性别 · 就诊科室 · 年龄 · 主诉 · 现病史/病史 · 既往史 · 体格检查 · 辅助检查 · 诊断（西医诊断 + 中医诊断）· 处理意见 · 草药处方 · 剂数 · 用法 · 备注 · 医师签名 · 就诊日期 |
| 6 | **历史诊断**面板：诊断性质 · 疾病编码（ICD，形如 B94.802）· 诊断名称 · 诊断注释 · 中医症候 · 主诊/疑似 · 开立医生；以及**历史医嘱**（西药：项目名称 · 规格 · 数量 · 频次 · 用法 · 开立时间 · 开立医生） |
| 7–11 | **历史医嘱（中药）表格**：项目名称 · 规格 · 组 · 单剂数量 · 频次 · 总量 · 付数 · 用法 · 医嘱类型 · 加急 · 开始时间 · 开立时间 · 开立医生 |

**关键结构性发现**：

1. **一次导出 = 一个时间序列**：5 次门诊就诊 + 4 份历史中药医嘱。**病案不是孤立记录，而是随时间演化的序列。**
2. **HIS 表格是高度结构化的**，字段远超普通病历：
   - 药味行含：规格、组号、单剂剂量、**频次（QD/BID）**、**总量**、**付数**、用法（内服）、开立时间、开立医生
   - 诊断行含：**ICD 编码**、诊断性质自定义、**主诊/疑似标记**
3. **"机械煎药（含 2 袋）"本身是一条医嘱行**（QD、14 付），说明代煎服务也是可计价医嘱项。
4. **跨专科就诊**：就诊科室为消化科门诊，而主病为带状疱疹后神经痛。→ **就诊科室 ≠ 疾病所属专科**，二者不可混用为一个字段。
5. **复诊主诉常为"服药后复诊"** —— 这不是真正的主诉，而是就诊类型。真正的主诉需从初诊继承。
6. **中医诊断可能只有证型、无病名**，且写法带冗余标点（如"湿热瘀阻证、"）。

### 2.3 两种来源的差异矩阵

| 维度 | 样本 A（手写教学表单） | 样本 B（HIS 病历） |
|---|---|---|
| 数据形态 | 自由文本（手写） | 结构化表格（印刷） |
| 辨证分析 | ✅ 有专门栏位 | ❌ 无 |
| 心得体会 / 导师点评 | ✅ 有 | ❌ 无 |
| 舌象脉象位置 | 独立「望闻切切诊」栏 | 混在「体格检查」栏内 |
| 处方明细 | 药名 + 剂量（手写） | 药名 + 剂量 + 频次 + 总量 + 付数 + 开立医生 |
| 诊断编码 | ❌ 无 | ✅ ICD 编码 + 主诊/疑似标记 |
| 辅助检查 | 自由文本 | 含检查日期、外院机构名、指标、数值、单位 |
| 就诊次数 | 1 页模板含 2 次复诊 | 每次就诊独立成页 |
| OCR 置信度 | ≈ **0.30**（手写） | **0.50–1.00**（印刷） |

**结论：同一个数据库必须同时容纳"高度结构化的 HIS 表格"与"完全非结构化的手写文本"这两个极端**，并用统一模型表达。

## 三、数据库的基本特点

从上述材料归纳出本数据库区别于普通业务系统的**八个基本特点**：

### 特点 1 · 多来源异构，同一病程数据分散在多种载体
同一患者的同一疾病，可能一部分来自手写教学表单、一部分来自 HIS 打印件、一部分来自 HIS 界面截图。**来源必须显式建模**，否则无法判断某条记录的可信度与解析策略。

### 特点 2 · 时间序列性 —— 病案是"病程"而非"快照"
一次导出即含多次就诊。**"一次就诊"是原子记录，"一个病程"是分析单元**，两者需要显式的聚合关系。

### 特点 3 · 教学属性与临床属性并存且可分
跟师学习记录 = 临床病案 + 学习元数据（心得、导师点评、签名）。二者必须**可分别查询**（例如"老师治某证用了哪些方"不应被心得文本干扰）。

### 特点 4 · 结构化程度呈两极分布
HIS 医嘱是精细表格（13 列属性/行），手写部分是纯自由文本。**任何"要么全结构化、要么全自由文本"的单极设计都会失败**，必须支持"结构化字段 + 原文保真"双写。

### 特点 5 · 中医术语的非规范化表达
- 中药普遍带**炮制前缀**：盐黄柏、醋莪术、醋三棱、炒酸枣仁、砂烫枳实、醋延胡索、黄芩片、甘草片、炒牛蒡子……
- 同一药存在多个炮制规格，**炮制品在处方语境下近乎独立药材**
- 证型写法多样，且常有冗余标点
- **归一化是统计准确性的前提**（这正是 `herb_aliases` 与 `herb_name_norm` 的价值）

### 特点 6 · 天然的"病—证—法—方—药"五层链条
```
西医诊断（可多条）  ┐
中医病名 + 证型     ├─► 治法 ─► 方剂（可选）─► 药味明细（含剂量/炮制/频次）
辨证分析（叙述）    ┘
```
这是一个**层级链**，每层可一对多，且必须能独立查询与统计。

### 特点 7 · 存在隐含的确定性约束
HIS 医嘱表存在算术不变量：**总量 = 单剂剂量 × 剂数**。

经本轮 14 条中药医嘱逐条检验，**14/14 全部成立**。这是一个不依赖任何模型的**确定性校验规则**，可用于自动发现 OCR 识别错误（见 §六）。

### 特点 8 · 数据质量不可控，真实录入不守规范
学生把检查结果填入「过敏史」栏；复诊主诉写成"服药后复诊"；中医诊断只有证型没有病名。**数据库必须容忍不完美的真实数据**，而不是假设输入是规范的。

## 四、基本要求

### 4.1 功能要求

| # | 要求 | 来源依据 |
|---|---|---|
| F1 | 容纳多种来源单据（手写表单 / HIS 打印 / HIS 截图），并记录来源类型 | 样本 A vs B 形态迥异 |
| F2 | 以"一次就诊"为原子记录，但支持聚合成"病程/疗程" | 样本 B 一次导出含 5 次就诊 |

| F5 | 诊断可多值：西医诊断多条 + 中医病名 + 证型，支持"仅证型无病名" | "西医诊断：A；B；C 中医诊断：某证" |
| F6 | 独立记录**辨证分析**叙述 | 样本 A 有专门栏位，原设计缺失 |
| F7 | 跟师学习元数据：心得、导师点评、双签名、日期 | 样本 A 第 3 页 |
| F8 | 医嘱级属性：频次、付数、总量、用法、开立医生、开立时间 | HIS 表格 13 列 |
| F9 | 诊断级属性：ICD 编码、主诊/疑似标记、开立医生 | HIS 历史诊断面板 |
| F10 | 辅助检查结构化：检查日期、机构、项目、数值、单位 | 外院生化结果 |
| F11 | 字段级溯源：每个结构化字段可追回原图位置 | 手写/印刷置信度差异大 |
| F12 | 满足算术不变量校验（总量 = 剂量 × 剂数） | 特点 7 |

### 4.2 非功能要求

| # | 要求 | 说明 |
|---|---|---|
| N1 | **离线可用** | 断网时录入、检索、macOS OCR、导出必须正常 |
| N2 | **录入速度** | 单份病案校对入库 < 2 分钟，否则学生不会用 |
| N3 | **数据不丢失** | 原始图片永久保留，附件与数据库一致性可自检 |
| N4 | **可扩展** | 为后置的证型/药物频次统计预留结构（舌象/脉象需可统计） |
| N5 | **单机性能** | 万级病案下检索可接受 |
| N6 | **审计留痕** | 病案修改不可抵赖 |

### 4.3 隐私与合规要求

本轮解析发现一个**原设计未预料到的严重隐私问题**：

> HIS 单据的「就诊卡号」字段形如 `YD-<地区码><出生日期><顺序码>`（前缀 `YD-`，后接 **18 位身份证号本体**）。本轮样本中该号码与患者身份证号完全一致，即**卡号内嵌了完整身份证号**。

**要求**：

| # | 要求 |
|---|---|
| P1 | **禁止明文存储内嵌身份证的卡号**；如需保留，必须哈希或截断 |
| P2 | 姓名、电话、卡号在**任何上云调用前**必须替换（脱敏中间件） |
| P3 | 原始扫描件与 OCR 全文**不得进入 Git**（已由 `.gitignore` 的 `data/` 覆盖） |
| P4 | 面向公开仓库的文档必须去标识化（本报告即按此处理） |
| P5 | AI 输出必须标注"仅供学习参考，不作为诊疗依据" |

| 表 | 字段 | 说明 |

| `prescription_items` | `group_no`（组） | HIS 有"组"列 |
| `prescription_items` | `spec`（规格） | HIS 有"规格"列 |

| `prescriptions` | `is_decocted`（是否代煎） | "机械煎药（含 2 袋）" |
| `diagnoses` | **`is_suspected`（疑似）** | HIS 有"主诊/疑似"标记 |
| `diagnoses` | `diagnosed_by` / `diagnosed_at` | 开立医生与开立时间 |
| `patients` | **`card_no_hash`** | 替代内嵌身份证的卡号明文（见 P1） |
| `prescriptions` | `is_patient_brought` | 患者自带方（手写件中"方拟\_\_\_加减治之"可能是引用成方） |

### 5.4 中药炮制的建模选择（待确认，见 §八）

炮制品（黄芩片、盐黄柏、醋莪术）在处方语境中**接近独立药材**。有两种建模方式：

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 炮制作为 `prescription_items.processing` 属性 | 简单，药材字典干净 | 统计"醋莪术用量"需按属性过滤 |
| B. 炮制品作为 `herbs` 中的独立条目 + 指向基原的 `parent_herb_id` | 统计直接、贴合 HIS 实际写法 | 字典规模膨胀，需维护基原关联 |

**倾向 B**：HIS 与处方实际书写都以炮制品为项目名，方案 B 与真实数据一致，且便于回答"老师用醋制品的频率"这类问题。

## 六、对 OCR 流水线的实测启示

本轮解析相当于一次小规模真实评测，得到**五条有数据支撑的结论**：

### 6.1 置信度可用于自动路由（强烈验证）

| 内容类型 | Vision 置信度 |
|---|---|
| 印刷体（HIS 打印） | **0.50 – 1.00** |
| 手写（教学表单手写内容） | **≈ 0.30** |
| 印刷栏位标签（模板印字） | **1.00** |

**置信度在印刷体与手写体之间形成了清晰的分层**，且模板印字稳定为 1.00。这直接支撑"低置信内容定向送云端精修"的设计 —— **阈值可设在 0.5 附近**。

### 6.2 印刷体错误集中于形近字 → 字典可自动纠正

实测错误样本（药名）：

| OCR 识别 | 正确 | 错因 |
|---|---|---|
| 黄苓片 | **黄芩片** | 苓/芩 形近 |
| 盐黄相 | **盐黄柏** | 相/柏 形近 |
| 醋获术 | **醋莪术** | 获/莪 形近 |
| 古參 / 苦參 | **苦参** | 字形 + 简繁混杂 |

**关键结论**：药名错误**几乎全部是形近字**，而正确写法基本都在药材字典中。因此 **`herb_aliases` + 编辑距离/拼音相似度匹配可以自动纠正大部分药名错误**，无需依赖大模型。这是字典表的**第二个价值**（第一是统计归一）。

### 6.3 数字与单位存在系统性混淆

| 识别 | 正确 | 模式 |
|---|---|---|
| 159 | 15g | **`g` → `9`** |
| 129 | 12g | 同上 |
| B1D | BID | `I` → `1` |

**`g` 被识别为 `9` 是本场景最高频的系统性错误**。这要求在 OCR 提示词中**显式声明该混淆模式**，并在后处理中做单位白名单校验（剂量的单位只可能是 g / 克 / 适量 等）。

### 6.4 表格结构会完全丢失（最严重的发现）

样本 B 的中药医嘱是**横向排版的 13 列表格**。Vision 的输出**按列而非按行**：

```
OCR 实际输出顺序：
  [所有药名] → [规格] → [单剂数量] → [频次] → [总量] → [付数] → [用法] → [开立时间] → [开立医生]

期望（按行）：
  黄芩片 | g | 15g | BID | 210g | 14 | 内服 | ...
  盐黄柏 | g | 15g | BID | 210g | 14 | 内服 | ...
```

**结果：15 味药与各自剂量的对应关系全部丢失。**

这是"仅用 macOS Vision 只能得到文本流、无法结构化"的**极端证据**。它把 `DEV-22 版面重建` 从"按 y 聚类成行"提升为最高优先级任务，且**必须支持表格结构重建（列归属）**，仅做分行不够。

### 6.5 页面方向需要处理

医嘱表格为横向排版（相对页面旋转 90°）。Vision 容忍了旋转、字符识别正确，但**阅读顺序被破坏**（这正是 6.4 的成因之一）。流水线需加入方向检测与矫正。

### 6.6 确定性校验可兜底

§三 特点 7 的算术不变量（总量 = 剂量 × 剂数，实测 14/14 成立）提供了**不依赖模型的校验手段**：

> 若 OCR 把某味药的剂量识别错（如 15g → 159），则该行等式**必然不成立**，系统可自动标记该行待校对。

这是本报告最有实操价值的发现之一 —— **在完全不调用大模型的情况下捕获一类高频错误**。

## 七、结论

1. **本数据库的核心复杂度不在"存病案"，而在"容纳两个极端"** —— 精细结构化的 HIS 表格与完全非结构化的手写记录，必须在同一模型下共存且可互相查询。
2. **病案必须建模为时间序列**（就诊 → 病程），而非孤立快照。
3. **教学元数据与临床数据必须可分离**，这是师承学习系统区别于普通 EMR 的根本点。
4. **归一化与保真必须双写**：结构化字段服务统计，原文服务溯源，二者缺一不可。
5. **原设计主体成立**，需新增 4 张表、修订约 12 个字段，其中 `syndrome_analysis`（辨证分析）是**明确的缺失**。
6. **手写体识别仍是最大风险**：样本 A 的手写内容识别基本不可用（置信度 0.30，文本严重失真）。这再次印证：**阶段二 B3 必须先跑评测基线再决定产品形态**。
7. **印刷体场景乐观**：样本 B 的印刷内容识别质量高，配合字典纠错与算术校验，**HIS 批量导入可能是比手写识别更快见效的方向**。

> **顺带的产品判断**：样本 B 揭示了另一个高价值路径 —— 若能做好 HIS 单据的结构化解析，学生可以**直接导入医院打印/截图的门诊记录**，完全绕过手写识别难题。建议在阶段二评估是否将其提升为与手写识别并列的主线。
